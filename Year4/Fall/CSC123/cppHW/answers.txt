Bubblesort.cpp

1. In the original code, lines 48-50 copied the students pointer during
   the swap. After A[k+1] = temp, both rosters pointed to the same array.
   When temp went out of scope, its destructor freed the array. That left
   A[k+1].students dangling. Printing the roster then read freed memory,
   and destroying the roster could try to free the same array again.

2. I changed students to unique_ptr<string[]>, used make_unique<string[]>
   to allocate the array, and removed the roster destructor. The unique_ptr
   frees the array automatically.

3. The original swap no longer compiled because it tried to copy rosters.
   A roster that owns a unique_ptr cannot be copied because the pointer
   has a single owner.

4. I replaced the three copy statements with std::swap(A[k], A[k+1]).
   This moves the rosters and transfers ownership of their arrays.

Matrixerror.cpp

1. In the original code, clean() freed the rows and row-pointer array.
   When the matrix went out of scope, its destructor read the freed
   row pointers and tried to free the same storage again. In C=A*B,
   the default assignment copied the temporary's pointer into C,
   leaking C's previous allocation. The temporary then freed the
   shared array, so C.printm() read freed memory. Incompatible matrix
   dimensions could also cause out-of-bounds reads. For example,
   multiply() reported the mismatch but continued into the loop.

2. I replaced the raw arrays with double1d and double2d and used
   make_unique to allocate them. Functions borrow storage by reference,
   and ownership moves when the storage is replaced. I removed clean()
   and the destructor so the smart pointers handle cleanup automatically.
   I added dimension checks to the arithmetic operations and enabled
   operator_testing() in main.


Observers_problem.cpp

1. In the original notify() loop (line 198), a panicky investor's
   update() can call dump(), which calls detach(). The erase on
   line 193 removes the entry the loop is visiting. This invalidates
   the iterator, so advancing it after update() returns is undefined
   behavior and can cause a segmentation fault.

2. I replaced the range-based loop in notify() with an explicit
   iterator. I lock the current investor's weak_ptr, advance the
   iterator, and call update() if the lock succeeded. If the investor
   removes its own entry, the iterator already points to the next one.

3. Small example of the same error:

   std::unordered_map<int, int> entries{{1, 10}, {2, 20}};
   auto it = entries.begin();
   entries.erase(it);
   ++it;  // Advances an invalid iterator
